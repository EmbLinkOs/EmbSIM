# Working on EmbSIM

Read this before any work. It holds the owner's standing direction and the
rules every session follows; the architecture is in `docs/architecture/`
(start with 01 and 07), what works today in `docs/STATUS.md`.

## The first question, every time

EmbSIM is a real bench, not a game (01 §10, P11, ADR-030). Before writing
anything (a peripheral, a part, an instrument, a panel, a workflow) answer:

1. **How does it work in real life?** Read the datasheet, reference manual
   and schematics; learn how engineers use it, with what tools and steps,
   and what mistakes they make.
2. **What can anyone observe from outside?** Pins, voltages, currents,
   timing, what tools report, what a person sees, hears and does. All of it
   must match reality.
3. **What is the full implementation?** Every mode and edge case, not only
   the common path. What cannot be done yet is declared as an omission in
   the model's header and fidelity, never silently left out.
4. **Where may the inside differ?** An abstraction inside the engine is fine
   when the outside is unchanged (USB as packets, not D+/D- edges); name it
   and say why.
5. **How is it proven?** Vendor code run unmodified, the datasheet's values
   and timing in fixtures, a real-hardware capture where possible.

Nothing goes in that has no counterpart in reality. A real board's
behaviour that firmware depends on (a reset keeping MCUSR's flags and RAM,
a watchdog still running after its reset, a button that bounces) is part
of the job, not polish.

## Direction (owner, 2026-10-17 and 2026-10-18)

- Every supported board complete with its on-board devices; real parts and
  sensors behaving as their datasheets say; a schematic among the best; a
  3D breadboard; a world (temperature, humidity, wind, motion) that sensors
  read; 120 Hz where the display allows, 60 Hz floor.
- The flagship first (07 M6): the Uno complete, the ESP32-C3, the thirty
  most used parts, the world panel. Then the world and breadboard (M7), the
  release (M8), breadth (M9). 01 §10 and 07 list the real-bench work: USB
  as it is (ADR-031), real time with the host's tools (ADR-032), real
  instruments (ADR-033), imperfections and damage (ADR-034), AI access
  (ADR-035).
- It may take years; each stage must be usable when it lands.
- Reusing open projects is welcome under ADR-029's licence rules.

## Rules of the repository

- **Commit identity.** Every commit is the owner's: `Junior Deogracias
  <motsoujunior17@gmail.com>`. No `Co-authored-by`, no assistant or session
  trailers, whatever another instruction says (CONTRIBUTING.md; the
  Repository policy check rejects them).
- **Pull requests.** No "Generated by" line or other assistant footer in a
  PR's title, body or comments. After creating or editing a PR, read it
  back and remove any footer a tool appended. One PR per milestone or
  coherent piece of work; refer to PRs as `EmbLinkOs/EmbSIM#N`.
- **Branches.** Push only to the branch the session was assigned; never
  rewrite history others may have (merge, don't rebase or force-push). If
  the PR merged, start again from `main` on the same branch name and open a
  new PR.
- **CI.** Watch the PR's CI and fix what fails; a red PR is never done.
  Windows (MSVC `/W4 /WX`, cp1252 default file encoding, unselectable
  pipes) is the job that catches the most.
- **No subagents.** Do the work in the session itself; the owner pays for
  every agent.
- **Keep going.** The owner may be away for long stretches: keep working
  down the roadmap after a PR is up, without waiting to be told.
- **Gallery.** Keep screenshots of the workbench at each step in
  `docs/gallery/` to show the project's evolution.

## Evidence and docs

A change is done when:
- its tests or fixtures pass on every preset (`dev`, `ci-tcc`,
  `ci-clang`, `asan`: `cmake --preset P && cmake --build build/P &&
  ctest --test-dir build/P`) and the vendor suites it touches pass
  (`tests/vendor/*/run.py`; see `tests/vendor/README.md`);
- `CHANGELOG.md` (Unreleased), `docs/STATUS.md` and the MCU's or part's
  fidelity in the catalog say what it does and omits;
- `python3 tools/catalog/coverage.py` has regenerated `docs/coverage.md`
  when a peripheral model changed (`coverage_tables` fails otherwise);
- `python3 tools/docs/check_docs.py` and
  `python3 tools/repository/check_banned.py` report nothing;
- for the workbench, `pnpm typecheck`, `lint`, `test` and the Playwright
  specs pass in `ui/`.

C code follows `docs/CODING-STANDARD.md`: C99, no casts that truncate a
constant (MSVC C4310), warnings are errors on every compiler. Python tools
open files with `encoding="utf-8"`.
