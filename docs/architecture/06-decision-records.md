# 06 - Architecture Decision Records

Each record: context, decision, alternatives, consequences, status. Records
are referenced from documents 02 to 05 and from the specifications by number.
A **Proposed** record becomes **Accepted** on the project owner's review; the
ones marked Accepted here were taken at the 1.0 baseline on 2026-10-15.

---

## ADR-001 A dependency-free C core as a library, built by GCC, Clang, TinyCC, EmbCC and MSVC

**Context.** The reusable simulator code (EmbCC's `tools/embsim`, 37 000
lines) is ISO C99 with no dependencies and compiles with EmbCC itself. The
earlier EmbSIM foundation chose a C99 kernel behind a shared-library ABI. The
owner requires the simulator to work with EmbCC, GCC, TinyCC and Clang; the
simulator must embed in other tools and run on three operating systems.

**Decision.** `libembsim` is written in C99 plus a documented C11 subset
behind portability macros (`ES_STATIC_ASSERT`, `ES_INLINE`, `ES_NORETURN`),
with no third-party runtime dependency. Optional subsystems vendor
permissively licensed C under `third_party/` behind build options. The public
API is `include/embsim/*.h` with an `es_` prefix, opaque handles, explicit
ownership and status returns; its ABI is versioned (SPEC-001). CI builds the
core with GCC, Clang and TinyCC on Linux, Apple Clang on macOS, MSVC on
Windows, and EmbCC's Linux host target when the compiler is available.

**Alternatives.** Rust core (strong safety, but no reuse of the C
interpreters without FFI wrappers, no TinyCC or EmbCC build, a second
toolchain for every contributor); C++ (richer abstractions, loses TinyCC and
EmbCC); Python core (the earlier foundation's orchestration; too slow for
instruction execution and analog solving, and a runtime dependency).

**Consequences.** Discipline on undefined behaviour and manual memory
management; a coding standard with banned constructs; every optional feature
has a build switch and a documented fallback.

**Status.** Accepted.

## ADR-002 Integer picosecond time base with rational clocks

**Context.** The foundation used nanoseconds; core clocks like 72 MHz have
fractional-nanosecond periods, and timers derived through prescalers drift if
periods are rounded. Analog solvers need fine step boundaries.

**Decision.** `es_time_t` is unsigned 64-bit picoseconds. Clocks are rational
periods with phase accumulators (03 §1). The protocol exchanges time as a
decimal string. Picosecond resolution is also the default threshold-crossing
bracket for analog bridges' lower bound; the practical default is 100 ps.

**Alternatives.** Nanoseconds (insufficient resolution); femtoseconds (2^64 fs
is five hours, too short); double seconds (not deterministic across
platforms, accumulates error); multiple local time bases (the EmbCC
simulator's per-core cycle counts: cannot order events across cores and
islands).

**Consequences.** 213 days of range; every conversion from cycles goes through
a clock; clients must use big-integer-safe handling.

**Status.** Accepted.

## ADR-003 One net graph with electrical pin models and solver islands; no board callbacks

**Context.** The EmbCC simulator wires boards through `struct board_io`
callbacks (`pin_out`, `pin_in`, `analog`, `spi`): each board hard-codes what
is on each pin and cannot host a user circuit. The foundation had nets with
digital drivers but no electrical meaning.

**Decision.** Every connection is a net joining pins; every pin carries a pin
model (SPEC-003 §2); the engine partitions nets into digital and analog
islands and inserts bridges. MCU GPIO models expose pin models like any
component. Boards are composites of catalog components on nets. There are no
pin callbacks between boards and MCUs.

**Alternatives.** Keep callbacks and add a net layer for user circuits only
(two connectivity models, a board's LED would behave differently from a
user's); SystemC-style channels (a C++ dependency and a different time
model).

**Consequences.** Boards become data; the MCU GPIO models must be rewritten
against pin models (the register behaviour is reused); performance work goes
into island partitioning and event batching rather than callbacks.

**Status.** Accepted.

## ADR-004 An in-core MNA analog engine; ngspice as an offline validation reference

**Context.** The earlier plan deferred the solver choice pending an experiment
with an established SPICE engine. Requirements: deterministic coupling with
the event scheduler at picosecond boundaries, live topology edits, embedding
without dependencies on three platforms, convergence diagnostics addressed to
circuit nodes the user sees, and the modest circuit sizes around an MCU.

**Decision.** The analog engine is written in the core (03 §5): MNA,
Newton-Raphson, trapezoidal/BDF2 with LTE step control, dense and sparse
direct solvers, device models from the standard literature. ngspice is a
development-time reference: golden fixtures are generated by scripts that run
ngspice on the same netlists and are committed with versions and tolerances.
No SPICE engine is linked into the product.

**Alternatives.** Link libngspice (BSD licence is acceptable; but its
timestep control cannot be driven by an external scheduler at event
granularity without patches, its global state forbids multiple islands and
sessions, it is a 300 000-line dependency to build on Windows, and
interactive rewiring requires restarts); a co-simulation adapter over a
socket (nondeterministic timing, slow); XSPICE's event-driven extensions
(same engine constraints).

**Consequences.** The team owns numerical robustness; model coverage grows
with fixtures; cross-checking against ngspice is a CI duty; an
ngspice-adapter remains possible later for high-fidelity validation runs.

**Status.** Accepted.

## ADR-005 Reuse EmbCC's cores and peripheral models by extraction behind the backend contract

**Context.** Document 09: the EmbCC simulator holds validated interpreters for
five core families, register-file loaders for SVD/ATDF/EDC, peripheral models
for STM32, nRF52, RP2040, PIC32 and PIC24, a GDB stub, loaders and analyses,
with golden fixtures held against QEMU. It terminates the process on errors,
uses a global `struct sim`, prints to stdout, and models boards through
callbacks.

**Decision.** Extract the core interpreters, bus, register files, peripheral
models, loaders, GDB stub and analyses into `core/mcu/` behind SPEC-009's
contract, one family at a time, keeping file-level provenance (origin
repository, commit, path, Apache notice) in each file header and in
`NOTICE`. Mechanical changes are made on extraction: `die()` to status
returns, globals into instance structs, output to session streams, board
callbacks to pin models. EmbCC's golden fixtures are imported as EmbSIM
differential tests before any behavioural change. Upstream authorship is
provenance, never a commit trailer.

**Alternatives.** Link EmbCC's `tools/embsim` as a library unchanged (its
error handling and globals make that unsafe for multiple instances); rewrite
the interpreters (years of validated work discarded); depend on QEMU or
Renode (large dependencies, no electrical model, slower iteration, different
licences).

**Consequences.** EmbSIM owns a fork of the simulator parts of EmbCC; fixes
are ported in both directions by hand with commit references; EmbCC may later
consume `libembsim` for `embsim` itself (owner's decision, 08 §Q3).

**Status.** Accepted.

## ADR-006 JSON descriptions validated by JSON Schema 2020-12; YAML through importers; alignment with EmbLinkRTOS hardware descriptions

**Context.** Components, MCUs, packages, boards, projects, scenarios and
libraries must be authored by people and consumed by a dependency-free C
core, a TypeScript workbench and Python tools. EmbLinkRTOS fixed YAML with
JSON Schema for SoC and board descriptions (its SPEC-014).

**Decision.** The canonical, machine-consumed format is JSON (UTF-8, no
comments) validated by JSON Schema 2020-12 files in `schemas/`. The core
contains a small JSON parser and a schema-shaped validator for the
constraints that matter at load; the Python validator applies the full
schemas in CI. Authors may write YAML; `embsim validate` and the importers
convert it. Board and MCU descriptions share field names and semantics with
EmbLinkRTOS's board and SoC YAML where the concepts coincide (`soc`,
`oscillators`, `leds`, `buttons`, `pins`, `console`), and an importer turns an
RTOS board file into an EmbSIM board draft.

**Alternatives.** YAML canonical (needs a YAML parser in the C core: a
dependency or a large vendored one); S-expressions (KiCad's choice;
unfamiliar to most authors, no schema tooling); a custom DSL (tooling cost).

**Consequences.** Schemas are versioned (`schema_version`) with a migration
tool; a JSON file can be generated from anything; the workbench edits JSON
through forms, never asks users to type it.

**Status.** Accepted.

## ADR-007 One session protocol (JSON-RPC 2.0) for every client; the workbench contains no simulation

**Context.** The foundation's rule that GUI code holds no simulation
behaviour is kept. Clients: a desktop app, a browser, the CLI, test harnesses,
other EmbLink tools, IDEs.

**Decision.** SPEC-008 defines one method set over stdio, WebSocket and
in-process transports. The CLI uses the in-process transport and so exercises
the same methods the workbench uses. Observations are notifications and
binary streams; controls are requests; every external change is a request
that acquires a timestamp in the session.

**Alternatives.** FFI from the workbench to the core (Tauri can do it, but
browser mode could not, and the protocol would exist anyway for CI); gRPC
(a large dependency for the C side); a REST-only API (no streams, no
notifications; the foundation's polling showed the limits).

**Consequences.** The protocol is a public contract with its own versioning
and conformance tests; latency of a round trip bounds interactive feel, so
the stdio transport stays local and the message set stays lean.

**Status.** Accepted.

## ADR-008 Workbench technology: TypeScript, React and Vite; Tauri 2 desktop shell; browser delivery from the CLI

**Context.** Requirements: three platforms from one source, a polished and
accessible interface, high-performance canvases for schematics and
waveforms, offline operation, a small install, contributors who know web
technology. Tools available in the development environment: Node 22, pnpm,
Rust 1.97.

**Decision.** The workbench is a TypeScript application built with Vite and
React, with a small state store, SVG scenes for schematic and board views and
canvas/WebGL for waveforms. Desktop packaging uses Tauri 2 (a Rust shell
around the platform webview) which spawns `embsim sidecar`. `embsim serve`
delivers the same assets to a browser. The UI code never imports Tauri APIs
directly; a platform adapter hides file dialogs, menus and the sidecar.

**Alternatives.** Electron (consistent rendering, but 150 MB installs and
higher memory); Qt/QML (native, but a C++ build and a second design system
for the browser mode); Dear ImGui (excellent for instruments, but immediate-
mode text rendering and accessibility fall short of the interface
requirements); Flutter (good, but Dart is foreign to the EmbLink ecosystem);
Svelte or Solid (lighter than React; React chosen for the size of its
ecosystem of accessible components and contributors).

**Consequences.** Rust is required only to build the desktop shell, not the
simulator; webview differences across platforms are tested in CI with
Playwright; the design system is implemented once in CSS tokens and shared
components.

**Status.** Accepted.

## ADR-009 Extension tiers: declarative composites, sandboxed Lua behavioural models, explicit native plugins

**Context.** Users must add components and boards without the core team. Most
parts are compositions of primitives or simple behaviours (a sensor's
transfer function, a display controller's command set); some need native
speed. Untrusted native code cannot be made safe by a shared-library loader.

**Decision.** Three tiers: (1) **declarative** descriptions composing
primitive and other components with parameters, no code; (2) **scripted**
behavioural models in Lua 5.4 (vendored, MIT), sandboxed with no `io`, `os` or
`debug` libraries, a bounded instruction budget per evaluation and a small
API (pins, parameters, state, time, scheduling, bus transactions) specified in
SPEC-013; (3) **native** plugins implementing the primitive model ABI, loaded
only from paths the user names explicitly, marked trusted in the project, and
versioned by ABI number. WebAssembly as a fourth tier is FUTURE, pending a
maintained C runtime.

**Alternatives.** Python models (a runtime dependency in the core; slow); only
native plugins (unsafe sharing); only declarative (cannot express a display
controller).

**Consequences.** The Lua tier becomes the main authoring path for sensors,
displays and protocol devices; a conformance harness runs the same fixtures
against any tier.

**Status.** Accepted.

## ADR-010 Toolchain profiles: the simulator runs images; building is a described, optional convenience

**Context.** The owner requires EmbCC, GCC, TinyCC, Clang and Microchip XC
compilers to work. The simulator's contract is the image format; compilers
differ in invocation, targets and output formats.

**Decision.** `libembsim` loads ELF (with DWARF) and Intel HEX and never
invokes a compiler. Toolchain profiles (SPEC-010) are JSON descriptions with
detection and command templates per target and output interpretation; the
CLI and workbench run them for build-and-run; projects reference a profile
optionally. EmbSIM itself builds under TinyCC, which is what "TinyCC support"
can mean for a host-only compiler.

**Alternatives.** Bake toolchain knowledge into the core (couples the core to
tools that change); require one toolchain (contradicts the requirement).

**Consequences.** A profile can be added by users; XC8 support for PIC16/18
depends on a core that does not exist yet and is tracked as FUTURE.

**Status.** Accepted.

## ADR-011 Fidelity declarations are mandatory; unsupported behaviour is observable under a session policy

**Context.** A catalog grows faster than validation; users must know what to
trust. The EmbCC simulator silently reads zero for unmodelled peripheral
space.

**Decision.** Every component, MCU, peripheral and core model declares
fidelity per tier with claims, operating range, omissions, provenance and
validation references (SPEC-005 §6). The session policy (`strict`, `warn`,
`permissive`) decides what an unsupported access or an out-of-range use does
(04 §4). Clients display fidelity and policy prominently; `strict` is the CI
default.

**Alternatives.** Best effort everywhere (unusable for verification);
refuse everything unsupported (unusable for exploration).

**Consequences.** Validation refuses a model without a declaration; the
catalog shows what is validated against what; STATUS.md stays honest with
little effort.

**Status.** Accepted.

## ADR-012 Virtual-time recordings of external inputs are the replay contract

**Context.** The EmbCC simulator records inputs by instruction step and
covers only the console and the debugger; EmbSIM has many input kinds, many
cores and analog islands.

**Decision.** SPEC-012: a recording is the ordered list of external inputs
with virtual timestamps and sequence numbers, the identities of everything
that shaped the run, and the discrete observations used to verify replay
(interrupt entries per core, probe events, run end). Replay is exact for
discrete state; analog values are compared with tolerances.

**Alternatives.** Full state checkpoints (large, version-fragile; may come
later for save and resume); step-based records (not meaningful across cores
and islands).

**Consequences.** Determinism of the scheduler ordering becomes a tested
invariant; every input path goes through the session command path.

**Status.** Accepted.

## ADR-013 Build and repository tooling: CMake with presets for the core and CLI; pnpm for the workbench; Cargo for the desktop shell; a thin Makefile; Python only for tools and CI

**Context.** Three platforms, five C compilers, a web application and a Rust
shell in one repository.

**Decision.** `CMakeLists.txt` with `CMakePresets.json` builds `libembsim`,
`embsim` and the C tests on every platform and compiler; a thin `Makefile`
wraps the common presets for Unix users and keeps a TinyCC path
(`make CC=tcc`); `ui/` is a pnpm workspace built by Vite; `desktop/` is a
Cargo crate built by the Tauri CLI; `tools/` are Python 3.10+ scripts used by
CI and authors, never required to build or run the simulator.

**Alternatives.** Meson (fine, less familiar to Windows contributors); a
single hand-written Makefile (the EmbCC way; no MSVC without a second
script); Bazel (heavy).

**Consequences.** CI has three toolchains; release packaging lives in
`desktop/` and `packaging/`.

**Status.** Accepted.

## ADR-014 Single repository; commits in the owner's identity; three stable merge checks

**Context.** The owner requires every commit and pull request in their name
with no co-author trailers. The RTOS repository established a policy of named
required checks and a branch ruleset.

**Decision.** EmbSIM is one repository holding core, CLI, catalog, workbench,
desktop shell, tools, tests and docs. Commits use the repository owner's Git
identity; no `Co-authored-by` or assistant trailers; a policy check rejects
them. Required checks on `main`: `CI merge gate`, `Documentation build`,
`Repository policy` (docs/engineering/repository-workflow.md).

**Alternatives.** Separate repositories per client (slower cross-cutting
changes while the protocol is young).

**Consequences.** A monorepo CI with path-aware jobs; a later split remains
possible along the protocol boundary.

**Status.** Accepted.

## ADR-015 Instruction timing is a declared estimate per core, with an exactness tier where a datasheet allows it

**Context.** The EmbCC interpreters estimate cycles from a cost table except
on AVR, where they are exact. Users must not mistake simulator timing for
hardware timing.

**Decision.** Each core backend declares a timing tier: `exact` (per
datasheet, AVR), `estimated` (documented cost table, Cortex-M and others),
`unmodelled` (one cycle per instruction). Every client labels timing with the
tier; STATUS.md lists tiers; benchmarks compare against hardware or QEMU
where fixtures exist. Peripheral timing (baud rates, timer periods) is exact
with respect to the modelled clock tree regardless of the core tier.

**Alternatives.** Claim cycle accuracy (false); model pipelines and caches
(FUTURE per core when a validated model exists).

**Consequences.** Timing-margin analysis uses min/max tiers of component
models, not the core's estimate.

**Status.** Accepted.

## ADR-016 Multiple MCUs, boards and cores share one scheduler and no mutable global state

**Context.** The EmbCC simulator has one global `struct sim`. Projects need
several boards and multicore parts.

**Decision.** Every instance (session, MCU, core, peripheral, island,
component) owns its state; the session's scheduler orders their events;
backends and models are reentrant with respect to instances. A conformance
test runs two sessions in one process with interleaved commands and asserts
identical results to two separate processes.

**Alternatives.** One MCU per process with inter-process wiring (slow,
nondeterministic).

**Consequences.** Extraction from EmbCC moves file-scope state into instance
structs before anything else.

**Status.** Accepted.

## ADR-017 Catalog provenance and licensing: only redistributable descriptions are vendored; device packs are referenced

**Context.** Vendor register descriptions and board artwork carry licences
that vary from Apache-2.0 (most CMSIS-SVD packs) to proprietary (Microchip
device packs, board photographs).

**Decision.** The catalog vendors only files whose licence permits
redistribution, each with its licence file and a provenance record (source,
URL, version, hash). Other inputs are referenced by name and resolved from a
user-supplied path (`--dfp`, library settings), as EmbCC's simulator does.
Artwork is original SVG drawn for EmbSIM or licensed for redistribution,
never a vendor photograph.

**Alternatives.** Vendor everything (legal exposure); vendor nothing (poor
out-of-box experience).

**Consequences.** A licence check in CI; a provenance field in every schema.

**Status.** Accepted.

## ADR-018 Cortex-M on the Blue Pill (STM32F103C8) is the first firmware target; RISC-V and AVR follow; Microchip families after

**Context.** The first acceptance scenario needs one MCU with a validated
interpreter, a redistributable register description, a common board and
toolchains the owner names (EmbCC, GCC, Clang). EmbCC already models the Blue
Pill with ST's SVD and its F1 GPIO, RCC, USART and TIM models; the RTOS
project's first targets are Cortex-M and RISC-V.

**Decision.** M1 extracts the Cortex-M backend and the STM32F1 models and
ships the Blue Pill as the first board, then the nRF52840 DK and the Pico
(already modelled in EmbCC) as the next Cortex-M boards; M4 adds RISC-V
(`virt`, then a SiFive or ESP32-C3 board), AVR (Arduino Uno) and the
Microchip families (Explorer 16/32, Curiosity) with XC16 and XC32 profiles.

**Alternatives.** Arduino Uno first (simplest core, exact timing, huge
audience; but its 8-bit AVR hides the register-file machinery the other
families need); Pico first (two cores and a boot ROM add complexity to the
first slice).

**Consequences.** ST's SVD redistribution terms are checked before vendoring;
until then the Blue Pill's register file is user-supplied as in EmbCC.

**Status.** Accepted; the register-file consequence is superseded by ADR-020.

## ADR-019 An MCU runs in quanta on the session's scheduler; its peripherals keep time inside the machine

**Context.** EmbCC's simulator steps one instruction at a time and tells its
running peripherals after each one how many cycles passed (`tick`), asking
them when their next interrupt comes (`next_event`) to skip idle waits.
SPEC-009 §6 first asked for peripherals that schedule their own session
events instead. The golden fixtures EmbCC's models pass depend on their
exact per-instruction timekeeping, and SPEC-009 §11.7 requires those fixtures
to pass before any behavioural change.

**Decision.** The MCU runtime (`core/mcu/mcu.c`) runs the machine as one
CORE event per quantum: up to the next session event that is not an analog
step, at most `core_quantum_ps` (1 µs by default), and ending early when a
pin changes so the circuit sees every edge at the instruction that made it.
Analog islands step up to the quantum's end. Inside the machine the
peripherals keep EmbCC's `tick` and `next_event` while their clocks run; a
sleeping core (WFI, WFE, a branch to itself) costs nothing: its next quantum
is the time its devices' next event comes, or the pin change that wakes it.
Cycles become picoseconds exactly, at the core clock the clock model reports
(the RCC ends a quantum when HCLK changes).

**Alternatives.** Peripherals as session events (SPEC-009's first text):
cleaner idle detection but a rewrite of every extracted model before its
fixtures could vouch for it. A fixed quantum without the next-event bound:
cheaper, but inputs would be seen up to a quantum late.

**Consequences.** Inputs from digital events are exact; inputs that come
from an analog comparator crossing are seen at the start of the quantum
after the crossing, at most `core_quantum_ps` late. The exception is the
core's own edge on an analog net: the next quantum waits out the edge's
ramp (its swing at the pin's slew rate, less than a cycle), so a device the
edge clocks answers before the core's next instruction (an SPI slave on a
clock line with an LED); the core goes on from where it stopped, its
timing unchanged. A breakpoint splits a
quantum without changing the run: the M1 test compares a stopped and
continued run with an uninterrupted one instruction for instruction.

**Status.** Accepted (M1).

## ADR-020 Register descriptions are EmbSIM JSON written from the reference manuals; vendor SVD files convert with a tool

**Context.** ST's STM32F103xx.svd (from the cmsis-svd-data collection,
version 1.3) carries STMicroelectronics' End User License Agreement: copies
for developing and distributing tools are allowed with its notices kept,
but it is not an open-source licence, and reverse engineering is
restricted. EmbCC requires the user to supply the file. Open question Q1
asked whether to vendor it. A test suite that runs on every platform cannot
depend on a file the user supplies.

**Decision.** The core reads one register format, EmbSIM's JSON register
description (`schemas/registers.schema.json`): peripherals, registers,
fields with the reference manuals' access notation (rw, r, w, rc_w0, rc_w1,
rc_r, rs, t), and the interrupt table. The STM32F103's
(`catalog/mcus/st/stm32f103c8/registers.json`) is written from RM0008 Rev 21
and PM0075, licensed with the project; ST's SVD is used only to check its
addresses and reset values on a developer's machine and is not shipped.
`tools/importers/svd2regs.py` converts any SVD a user holds into a
description for their own use. An MCU description names the format
(`register_file.format: "embsim"`).

**Alternatives.** Vendor the SVD with ST's licence beside it (legal review
per vendor; non-free content in the catalog). Parse SVD in the core (EmbCC's
1600-line reader with its exits; still needs a file the tests cannot ship).

**Consequences.** The Blue Pill runs out of the box and in CI. Where the
manual and ST's SVD disagree, the manual wins (TIM ARR resets to 0xFFFF, SPI
I2SPR to 0x0002). Adding a part means writing or converting its description;
the validator checks overlaps, field widths, access codes and interrupt
names. Q1 is closed.

**Status.** Accepted (M1).

## ADR-021 A ROM whose code cannot be shipped has its documented functions done by the host

**Context.** A program built with the Pico SDK calls the RP2040's bootrom
through its tables: memcpy and memset, the bit operations, the flash
programming functions, and the float and double libraries behind every
`float` and `double` operation. Raspberry Pi's bootrom source (pico-bootrom,
BSD-3-Clause) holds a float library whose licence allows its use only on an
RP2040, or under GPLv2 from its author: neither may ship in EmbSIM, and a
simulator is not an RP2040. Without the functions the SDK's runtime calls a
null pointer before `main`.

**Decision.** The ROM holds what the part's documentation says a program
finds there (the header, the tables, their codes and layouts) and each
function is `bkpt #n` followed by a return. A core that executes such a
`bkpt` calls the machine's `rom_call` (`core/mcu/mach.h`), which does the
function in C with the core's registers, flags and memory, and charges its
cycles; any other `bkpt` is a breakpoint instruction as before. The
RP2040's functions are `core/mcu/rp2040/rom.c`, written from the RP2040
datasheet's description of the bootrom (2.8.3) and the behaviour the SDK
relies on, with the bootrom's float conventions (denormals as zero, no NaN
out, conversions towards minus infinity).

**Alternatives.** Running the bootrom's code (not distributable). A
clean-room bootrom compiled to Thumb from C with a permissively licensed
soft-float library (compiler-rt): the functions' code paths would be the
core's own, but a committed binary blob, a cross toolchain to rebuild it and
a soft-float port to keep, for no behaviour a program can see beyond timing.

**Consequences.** Unmodified Pico SDK images run (`tests/vendor/pico-sdk`).
The functions' timing is estimated per call (ADR-015), not cycle by cycle;
the transcendental functions are the host's libm rounded once, so they may
differ from the bootrom's, and between hosts, in the last place. Other parts
whose ROMs are not shipped (an nRF52's MBR, a SAM's ROM) can take the same
route.

**Status.** Accepted (M6).

## ADR-022 Continuous canvas preferences and reload-safe static serving

**Context.** The finite SVG sheet left an inconsistent gray region after pan/fit.
Canvas appearance needs local customization across views without changing project
connectivity. Reload testing also exposed the single-client server waiting on the
old WebSocket while the browser waited for its next document.

**Decision.** Render a viewport-covering background with world-anchored CSS
patterns, updating its transform with the scene. Keep validated, versioned
appearance preferences in local storage with an in-memory fallback; editing snap
and electrical project data are independent. Use theme-aware palettes and native
keyboard controls. The single-threaded native server services one auxiliary HTTP
request between session polls, with a short request-head deadline. Auxiliary
connections retain authority checks and cannot upgrade to another session.

**Alternatives.** Enlarge the finite sheet (still exposes an edge); store appearance
in project JSON (unnecessary project churn); close the session on reload or add a
server thread (couples navigation to runtime ownership or adds concurrency).

**Consequences.** Pan/zoom never reveals a different workspace surface. Reloads
and asset fetches work with an active session, preserving its notification target.
The server remains cooperative rather than a general concurrent HTTP server;
static transfer and request timeouts still bound its work. Tests cover pixel
uniformity, preferences, active-session asset delivery and request restrictions.

**Status.** Proposed; implemented for review in this pull request (2026-10-16).

## ADR-023 A CMOS output's Thevenin source is its rail; VOH and VOL are the levels at the rated load

**Context.** SPEC-003 §4 gave a digital output on an analog net a source of
`voh` or `vol` through `rout`. Those are a datasheet's guaranteed levels at
the rated current (an STM32F103's 0.4 V at 8 mA): a CMOS output's
transistors pull to its rails, and at a light load it sits within
millivolts of them. With the levels as sources, a Blue Pill's PWM through a
10 kOhm, 4.7 uF low-pass averaged between 0.4 V and 2.9 V, so 25 % read
1.0 V on the ADC where the part reads 0.8 V; any measured output, an LED's
current or a divider's voltage, was off the same way.

**Decision.** A pin model has open-circuit levels, `voc_high` and
`voc_low`, behind `rout`. When a description does not give them, a CMOS
family's are its rails (`nominal_v`, which follows an MCU's io supply, and
0 V) and a TTL family's are `voh` and `vol` (a totem pole's high level is a
diode drop below VCC whatever the load). `voh`, `vol` and `rout` keep their
meaning: with the rails as sources, `rout` gives the drop at a load.

**Alternatives.** Deriving the source from `voh` and a rated current (one
more parameter per family, and the same rails for CMOS). Keeping the levels
and lowering `rout` (wrong at every load but one).

**Consequences.** CMOS outputs on analog nets measure as on the part;
currents through them rise accordingly (an LED from a 3.3 V output). The
component fixtures and the examples' scenarios pass unchanged; `test_analog`
follows the rails, and checks a TTL driver's levels and a description's
override.

**Status.** Accepted (M6).

## ADR-024 Transactional schematic repair and scoped drawing checks

**Context.** Manual wire creation alone cannot support sustained drafting. Users
need to reshape existing tracks, edit repeated parts precisely and find drawing
problems without accidentally changing electrical connectivity. Browser diagnostics
must not be confused with the authoritative native simulator's validation.

**Decision.** Express repair operations through the existing project-diff and
transaction history. Shift a selected segment perpendicularly while retaining its
original endpoints and same-net interior contacts through spurs. Keep geometry
clearing distinct from terminal disconnection. Batch only matching parameter
contracts with explicit field inclusion and mixed-value indication. Reject stale
source revisions and concurrent mutation snapshots; keep failed history entries.
Run deterministic structural and bounding-box checks in a cancellable inline worker,
key results to the project/catalog revision, and provide target navigation and
ordinary transactional routing repair. Classify unused pins as information and
state the report's limited scope in the interface.

**Alternatives.** Rebuild connectivity from drawn line intersections (conflicts with
SPEC-007's authoritative nets). Let each field create its own batch transaction
(partial edits and excessive undo steps). Run checks on the canvas event loop or
silently reuse old results (blocks interaction or presents obsolete findings).
Present visual checks as ERC (overstates what the descriptions and engine verify).

**Consequences.** Repair is undoable and layout-only where intended. Extra spur
tracks may be introduced to preserve junction contacts. Later automatic routing
can replace manually edited geometry; this is not a persistent constraint system.
Bounding rectangles include whitespace and can produce warnings needing review.
Pairwise geometry checks are not qualified for arbitrary sheet sizes; worker
cancellation and a 20-second deadline bound their lifetime. Full electrical rules,
physical clearance checking and large-sheet qualification remain future work.

**Status.** Proposed; implemented for review in this pull request (2026-10-16).

## ADR-025 Persistent flat schematic groups and native placement locks

**Context.** Larger schematics need named organization and protection of completed
placement. Client-only flags would be lost on save and bypassed by native edits.
Groups must not silently turn into electrical connectivity or simulator hierarchy.

**Decision.** Store flat groups under project.layout.groups and boolean placement
locks in instance layouts. Each top-level instance belongs to at most one group.
Native loading and transactions validate memberships; instance removal prunes
empty groups. Locked placement requires an explicit unlock before changing
position/orientation; omitted flags preserve existing locks. Automatic placement
uses locked bodies as fixed obstacles; direct transforms refuse mixed locked
selections atomically. Existing diff/transaction history persists organization
without resetting simulation. Copied complete component groups remap identifiers
and unlock copies. Export top-level explicit-data inventory through the existing
platform adapter rather than claiming an effective manufacturing BOM.

**Alternatives.** Local browser-only metadata (fails cross-client persistence).
Treating groups as composite electrical models (changes connectivity and scope).
Partially moving locked selections (surprising relative placement changes).

**Consequences.** Groups remain visual and flat; no hierarchical sheet editing is
introduced. Placement locks do not prevent explicit deletion or electrical edits.
Routing can replace manual geometry near a fixed component. Export groups exact
explicit parameters; defaults, unit equivalence and board internals are not
resolved. Existing schema version remains 1 with optional additive fields.

**Status.** Proposed; implemented for review in this pull request (2026-10-16).

## ADR-026 The world: an environment and physical objects that sensors read

**Context.** Sensors are the parts people wire to boards most, and today each
takes its quantity from a parameter or a slider on the part itself. Real
sensors share one room: a DHT22 and a BME280 on the same bench read the same
air, an HC-SR04 sees the object in front of it, an IMU moves with the board.
The owner's direction (01 §9) asks for temperature, humidity, wind, movement
and more, set by the user and felt by every sensor as in the real world.

**Decision.** The engine holds a world beside the circuit:
- **Fields**: ambient quantities (temperature, relative humidity, pressure,
  illuminance, sound level, wind velocity, magnetic field, gravity),
  uniform by default and optionally given as a function of position.
- **Bodies**: objects with a pose and a shape (a box, a sphere, a mesh's
  bounds), static or moving along a path or under a simple physics step;
  boards and parts placed in the 3D view are bodies too.
- **Queries**: a component model asks the world for a field's value at its
  position, for the nearest body along a ray (distance sensors, IR), for its
  own acceleration and rotation (IMUs), through the model API (C and Lua).

The world is engine state, stepped on the scheduler in virtual time, never
from the wall clock. Changing it is an input event like a button press,
timestamped, recorded and replayed (SPEC-012). A part's own parameter, when
set, overrides the world, so existing projects and fixtures keep their
behaviour. The workbench edits the world from a panel first (M6) and from
the 3D scene later (M7).

**Alternatives.** Per-part sliders only (today; no shared environment, no
motion). The 3D engine's physics as the source of truth (would put
simulation in the client, against P1, and break determinism). A full
physics engine in the core from the start (cost before need; a simple
kinematic step covers the flagship's sensors, ADR-029 governs any library
brought in later).

**Consequences.** Sensor models gain a uniform way to read the environment,
and fixtures can set the world as scenarios set inputs. The world's
fidelity is declared like a model's: it supplies what a sensor would
measure, not a thermal, fluid or structural analysis (01 §6). The protocol
gains world methods and a world description in the project (schema
additions, SPEC-005 and SPEC-008).

**Status.** Accepted direction (owner, 2026-10-17); design details proposed
until the specifications are written.

## ADR-027 The breadboard is a second editor of the same nets, drawn in 3D

**Context.** Q7 deferred a breadboard view past 1.0. The owner wants a 3D
bench where parts sit on breadboards and are wired with jumpers, as
learners and makers build circuits, and where the world of ADR-026 is
visible and touchable.

**Decision.** The project keeps one connectivity graph. The breadboard view
is another layout of it, as the schematic is:
- a breadboard is a component whose internal strips are its nets (its model
  connects the holes of a strip);
- a part placed on holes connects its pins to those strips;
- a jumper wire between holes is a wire, an edit of the project's nets
  through the same transactions and undo as the schematic's.

Either view shows what the other drew: a net made on the breadboard appears
in the schematic, unrouted until laid out, and the reverse. The view is
drawn with a WebGL scene (Three.js, Q12) from glTF models, with a 2D
top-down fallback; layout positions live in the project beside the
schematic's (`layout.breadboard`). Parts without a 3D model show a labelled
box with their pins at the right pitch.

**Alternatives.** A picture of the circuit derived from the schematic (no
building on the breadboard). A separate breadboard document (two sources of
truth that drift). A game engine shell around the workbench (heavy, harder
to keep accessible and themable, P1 still applies).

**Consequences.** Q7 is closed in favour of the view, scheduled for M7. Part
descriptions gain optional 3D model references and pin offsets. Accessibility
needs care: every breadboard action has a keyboard and list equivalent, as
the schematic's do.

**Status.** Accepted direction (owner, 2026-10-17); M7.

## ADR-028 Frame budgets: the display's rate, the simulation never waits

**Context.** The owner asks for an interface that runs smoothly, at 120 Hz on
displays and machines that offer it and 60 Hz elsewhere. 01 §8 already asks
for 60 Hz interaction on a 500-component schematic.

**Decision.** The workbench draws at the display's rate from the latest
state it has; the simulation runs in the native engine and streams to it
(SPEC-008), never waiting on a frame. Budgets, measured in CI on a
reference configuration: a frame's work under 8 ms on a 120 Hz display and
under 16 ms at 60 Hz for interaction (pan, zoom, drag, typing) in the
schematic with 500 components, the instruments at their widest, and the 3D
bench with 50 parts; streams are decimated to what a frame can show.
Rendering moves to WebGL where SVG or 2D canvas misses the budget. A
measurement that misses its budget fails CI like a test.

**Alternatives.** Best effort without budgets (regressions go unnoticed).
Moving simulation into the client for responsiveness (breaks P1 and
determinism).

**Consequences.** A frame-time harness joins the browser tests; the
schematic's renderer and the instruments may need WebGL paths; the 3D view
carries level-of-detail and a 2D fallback for machines that cannot meet the
budget.

**Status.** Accepted (owner, 2026-10-17); the harness is planned with M7.

## ADR-029 Reusing outside projects: permissive code, recorded assets, GPL as referees

**Context.** The owner welcomes reusing open projects to go faster. EmbSIM is
Apache-2.0 (01 §4); a careless copy can make the whole project
undistributable under it.

**Decision.** Three classes:
- **Code under permissive licences** (MIT, BSD, Apache-2.0, zlib, ISC) may
  be brought in or depended on, with its notice in `NOTICE` and its origin
  recorded as for EmbCC's code (P6). Candidates: avr8js and wokwi-elements
  (MIT), Three.js (MIT), Rapier (Apache-2.0), ngspice (BSD, already used as a
  referee).
- **Assets under attribution or share-alike licences** (KiCad's 3D models,
  CC-BY-SA 4.0 with an exception for designs that use them; Fritzing's
  parts, CC-BY-SA) may be shipped as separate files in the catalog with
  their licence and attribution recorded per asset, never merged into code.
- **GPL and other copyleft code** (QEMU, simavr, SimulIDE, ngspice's GPL
  parts if any) is never copied in. Such projects may be run as separate
  programs to referee our models (as QEMU referees the DSP instructions),
  and their documentation and behaviour studied; our models are written
  from datasheets and vendor references.

Proprietary simulators (Proteus, Tinkercad's) are studied only through their
public documentation and behaviour.

**Alternatives.** No reuse (slower, and loses well-made permissive work).
Relicensing under GPL to reuse more (forecloses users and integrators who
need Apache-2.0).

**Consequences.** A new dependency or asset set comes with a licence review
in its pull request; `tools/repository` checks that each vendored asset
directory carries a licence file. 09 §4 lists the projects assessed.

**Status.** Accepted (owner's reuse direction, 2026-10-17).
